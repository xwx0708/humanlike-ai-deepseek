# 项目总评（2026-11-02）

> 由 Claude（claude-opus-5-5）与 GPT（gpt-6.1-sol）在「Claude-GPT 协作台」讨论后写成，会话「类人AI项目总评」。
> 依据：通读 CLAUDE.md、README、00-总纲 全部文档、各模块 README 与待议问题，以及 src/、tests/ 的代码。
> Claude 实际运行了 `pytest -q`（224 passed，4 个 live 用例未跑）和 `ruff check src tests`（无报错）；GPT 只做了静态审阅。
> 这是一份评价，不是决策；其中的建议要用户认可后才算定下。

## 一句话定位

**设计辨识度高、工程骨架扎实，但核心体验和长期边界尚未验证的记忆型陪伴 AI 原型。** 总分 **6.5 / 10**（双方一致）。

## 长处

1. **立意清楚、有辨识度。** "不靠长上下文，靠会遗忘、会模糊、会自己浮现的记忆"是一个明确的主张，记忆时钟、常驻栏、浮现区、档案与残影都围绕它展开，不是泛泛的 RAG。
2. **过程治理少见地好。** 决策日志（D1～D43）、偏离记录、"我的设想 / 补充"分开标注、待你确认清单，让每个设计选择都能追溯到用户原话和理由。
3. **记忆模块的存储与整理部分完成度高。** src 约 8000 行，其中记忆约 5200 行；测试 224 个全过、ruff 干净；有模块边界测试（`tests/test_module_boundaries.py`）、参数注册表和 `data/plugins/` 可替换点。
4. **用真实模型校准过。** 提示词用真实 Qwen 跑过；发现模型违反提示词时补 Python 硬规则兜底（例如画像里的相对时间词），而不是只改提示词。
5. **后台有基本的健壮性。** 短事务、整理进度可恢复、删除时的版本检查都已做。

## 主要问题与风险（按严重程度）

1. **运行期上下文没有总预算，可能重新变成"越来越长的上下文"。** `memory/resident.py` 的 `resident_block` 取全部画像事实加全部常驻事件线，免竞争项没有总量上限；`memory/fresh.py` 只按强度阈值筛，没有 token 上限。长期使用后会持续膨胀，直接冲击项目的核心主张。
2. **记忆内容被当成系统指令，存在持久化提示词注入风险。** `response/responder.py` 运行期把常驻、浮现、新鲜记忆（含用户原文、附件摘录、模型生成的摘要）直接拼进 system；同时 `astrbot_plugin/main.py` 的 `_tools` 把 AstrBot 的全部工具交给模型。"只回主人"挡不住主人转发的恶意文件。
3. **"想起—使用—加固"没有闭环。** `scanner.use_memory` 已写好但回应模块没接（偏离 #12），主动检索 `search_memory` 没交给思考模型，纠错（"你记错了""改一下"）流程未定。所以"记忆已完成"应改为"存储与整理完成，使用闭环未完成"。
4. **最关键的端到端没有验证，状态口径混乱。** README 写回应模块"接上 QQ 后实际对话还没测过"，待办.md 却写"已能用：QQ 私聊收发"；待办.md 还写着"上下文用到约 70% 才会启动"，而 D43 已改为约 6 万 token。收发验证、工具验证、启动后记忆行为验证三件事没有分开记录。
5. **没有评估体系，大量数值是"暂定"。** "像不像人"怎么评、长期运行模拟、和普通最近窗口记忆（`RecentWindowMemory`）的对照都还没做。遗忘曲线、记忆时钟、常驻加权竞争、矛盾掷骰子等机制很精巧，但在没有数据前调参空间过大，效果无法证明。
6. **错误记忆会固化。** 小模型抽取的事实进入画像后不遗忘，还会让来源事件线免竞争常驻；格式校验只保证合法，不保证正确。纠错流程缺失让这一点更严重。
7. **"彻底删除"的承诺超过实际覆盖范围。** `ThreadStore.erase_thread` 认真删了摘要、画像、日志，但人物和别名仍保留，AstrBot / QQ / 附件缓存 / 模型服务商的副本也不在范围内。对用户的说法应明确边界。
8. **并发一致性（静态推断，未复现）。** `on_private` 没有按会话串行化，平台并发派发时回复可能乱序；`action/qq_self.py` 的限频是"调用前检查、成功后记录"，并发时可能穿透。
9. **小问题。** `resident_block` 把用户写死成"他"；分工表名义上多对话分工，实际回应、行动多由总纲对话代写，模块 README 的"负责对话"与实际不符。

## 讨论中修正过的判断

- Claude 起初认为"情绪模块 0 行、严重偏科"是大问题；GPT 认为先做记忆 + 回应是合理的阶段选择。**结论：不作为主要扣分项。**
- Claude 起初写"行动只有 QQ 自身操作"；GPT 指出插件把 AstrBot 全部工具交给了模型。**结论：行动是"工具面宽、本项目的约束窄"。**
- 不能因文档矛盾断言 QQ 从未实测，只能说"验证层级没有记清"。

## 建议的下一步（按顺序）

1. **给运行期上下文加总预算**：常驻、浮现、新鲜记忆各自配额，超出时按得分截断；把记忆内容作为"不可信资料"与系统指令分开放置。
2. **接上 `use_memory` 和主动检索**，补齐"想起—使用—加固"闭环；同时把 README、待办的状态统一成"收发验证 / 工具验证 / 启动后记忆验证"三档，修掉过时的"70%"。（启动后的端到端冒烟测试可以和这一步并行先做。）
3. **做正式评估**：模拟长期对话，与 `RecentWindowMemory` 对照，控制同一思考模型、同一输入 token 预算；再据结果决定情绪模块和各"暂定"数值。

其后再处理：纠错流程、删除边界的说明、会话串行化与限频原子化。
